# Plan mode

計画は、いのまさが席を外したあとも同じ仕事として完走するためのもの。手順の網羅ではない。

## 書く前

材料なしで計画を出すな。先に調べる。

- リポと既存成果（コード、成果物、lock、前回の失敗）
- ソースの実数（想定の番号範囲ではなく、揃っているペア）
- 共有資源の状態

在庫・本数・欠けは計画の材料。実行の止め条件にするな。数えられるものを「実行で見て、欠けたら聞く」に先送るな。

## 計画書に書くこと

この見出しだけ使う。順番の章は書かない。やらないことの章は書かない。範囲はタスクの粒で切れ。

**目的**  
なんのためにやるか。目標の手前。

**目標**  
終わったときに何があるか。パス、本数、成果物。達成したかが分かればいい。

**条件**  
守る制約。途中で変えたら別の仕事になるもの。Planモードで確定するものはここ。調査で分かった本数・現状も条件に書け。

**注意事項**  
壊しやすい点。重ねると死ぬもの、熱、lock。工程表ではない。

**イレギュラー対処**  
実行中の想定外の扱い。計画前に調べれば分かったことをここに逃げるな。

**緊急停止**  
回し続けたら損になるときだけ（データが使えない、OOM、1 step が分単位）。成果物の身分が変わらない欠けで止めるな。

**現状**  
いま何があるか。計画はここからの差分。ゼロから書くな。

**時間**  
何時間が payload か。席を外せる根拠。無い計画は一晩を守る設計になっていない。

**タスク**  
実行可能な粒。1タスクに「誰が / 何を / 何をもって終わりか / 何を触らないか」。前の終わりが次の入力（受け渡し）。終わりの印は確認（本数一致、成果ファイルがある、queue empty）。ToDo の羅列にするな。

**サブエージェント**  
誰が親か。サブは何を渡され、何を返し、何を触らないか。並列できる作業と、親が直列で持つ共有資源（学習、キュー消費、本番プロセス）を書け。箱と矢印の自己満は要らない。

## 聞くこと

Planモードで聞くのは、成果物の身分が変わるものだけ（トークン数、step、場所、データの差し替え）。身分が同じ messy（欠番があるがペアは数十本ある）は、調査結果を条件に書いてデフォルトで進む。

実行承認のあと、安い不確実性で止まって聞くな。止まって待つコストは失敗の一種。
